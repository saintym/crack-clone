## 무슨 일이 있었나
기억 기록은 10턴마다 배경에서 도는 핵심 기능이다. 단위·통합 테스트 415개가 전부 통과했다. 그런데 실제 PostgreSQL에 붙여 브라우저로 플레이해 보니, **첫 기록이 끝난 뒤부터 기록이 전혀 돌지 않았다.**

## 증상 / 막힌 지점
- 재현 조건: PostgreSQL, 기록이 한 번 DONE이 된 스토리에서 다음 기록을 트리거
- 에러 원문:
```
could not determine data type of parameter $4
```
  SQLState는 `42P18`이었다.
- 겉으로 보이는 증상: 자동 기록은 오류 로그만 남기고 조용히 넘어갔다. `POST /memory/record`는 500이었다. 기록할 것이 없어서 `NOTHING_TO_RECORD`여야 하는 경우도 500이었다.
- 처음에 의심한 것: 트리거 조건 계산(마지막 기록 턴 비교)이 틀렸다고 봤다.

## 원인
- 진짜 원인: 수정된 턴을 찾는 JPQL에 `(:since IS NULL OR m.editedAt > :since)`가 있었다. `since`가 null이 아닐 때 PostgreSQL이 파라미터 타입을 추론하지 못한다.
- 확인한 근거: 같은 쿼리가 H2에서는 통과한다. 첫 기록 전에는 `since`가 null이어서 분기를 타지 않아 동작했고, 첫 DONE 이후에만 실패했다. 기록을 되돌려 DONE을 없애면 다시 동작했다.
- 왜 바로 못 찾았나: 테스트가 전부 H2였다. 그리고 실패가 로그에만 남고 화면에는 아무 표시가 없어서(배경 처리 설계), 브라우저로 10턴을 플레이한 뒤에야 "뱃지가 다시 안 뜬다"로 드러났다.

## 해결
- `since` 유무에 따라 쿼리를 둘로 나눴다. 타입 캐스트(`CAST(:since AS timestamp)`)는 Hibernate 방언에 의존하는 부분이 있어 피했다.
- H2에서는 재현되지 않아 회귀 테스트를 두 겹으로 넣었다. 하나는 분기 호출 검증, 하나는 **모든 `@Query`에 `:파라미터 IS [NOT] NULL` 패턴이 없는지 검사하는 정적 가드**다.
- 확인 방법: 스크래치에 임시 PostgreSQL 클러스터를 띄워 V1~V7을 적용하고, 기록을 연속 4회 DONE까지 확인했다. 전체로는 기록 9회 성공, 실패 0회, 앱 로그에 ERROR/WARN 0건이었다.

## 왜 이 방법을 골랐나
- 버린 대안: 테스트 DB를 Testcontainers로 바꿔 PostgreSQL에서 돌리는 것. 시간이 더 걸려서 이번에는 정적 가드로 막고, 후속 과제로 남겼다.
- 이 선택으로 포기한 것: 같은 유형의 다른 방언 문제는 여전히 잡지 못한다. 가드는 한 패턴만 막는다.
