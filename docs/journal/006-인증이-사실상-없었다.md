## 무슨 일이 있었나
브라우저로 UI를 검증하다가 인증을 확인했다. 토큰 자리에 아무 문자열이나 넣어도 모든 API가 200을 돌려줬다.

```
curl -H "Authorization: Bearer aaa.bbb.ccc" http://localhost:8082/api/scenarios
→ 200
```

## 원인
- 진짜 원인: `AuthFilter`가 토큰을 **길이만** 봤다.
```kotlin
if (token == null || token.length <= 10) { /* 401 */ }
```
  `AuthController.isValidToken`도 같았다. 주석에는 "stateless, password is the gate"라고 적혀 있었다. 비밀번호가 관문이라는 전제였는데, 관문을 통과했다는 증거를 검증하지 않았으니 관문이 없는 것과 같았다.
- 왜 바로 못 찾았나: **성공 경로만 확인했기 때문이다.** 로그인해서 토큰을 받고 API가 되는 것까지만 봤다. 틀린 비밀번호, 위조 토큰, 만료를 한 번도 밟지 않았다.

## 해결
- 토큰을 `payload.signature` 형식으로 발급했다. `payload`는 base64url(`v1:<만료 epoch 초>`), `signature`는 HMAC-SHA256(payload, `crack.auth.token-secret`)이다. 비교는 상수 시간으로 한다.
- `AuthFilter`와 `/api/auth/verify`가 서명과 만료를 모두 검증한다. 유효 기간은 `crack.auth.token-ttl-hours`(기본 720시간), 무효화는 시크릿 교체로 한다.
- 확인 방법: 단위 테스트(위조·만료·다른 시크릿)와 필터를 포함한 API 테스트를 넣고, 실제 앱에서 다시 재현했다.

| 요청 | 수정 전 | 수정 후 |
|---|---|---|
| `Bearer aaa.bbb.ccc` | 200 | 401 |
| 80자 임의 문자열 | 200 | 401 |
| 헤더 없음 | 401 | 401 |
| 로그인 토큰 | 200 | 200 |
| 틀린 비밀번호 로그인 | 401 | 401 |

테스트를 쓸 때도 한 번 틀렸다. 서명 마지막 글자를 `A`로 바꿔 위조를 만들었는데 원래 값이 `A`여서 같은 문자열이 됐고, 테스트가 통과해 버렸다. 반드시 다른 글자로 바꾸도록 고쳤다.

## 왜 이 방법을 골랐나
- 버린 대안: 서버에 세션 저장소를 두는 것. 개인용 단일 인스턴스에 상태를 늘릴 이유가 없었다.
- 이 선택으로 포기한 것: 개별 토큰 무효화. 시크릿을 바꾸면 전부 무효가 된다. 혼자 쓰는 앱이라 충분하다.
