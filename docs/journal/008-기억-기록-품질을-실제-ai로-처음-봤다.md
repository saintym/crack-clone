## 무슨 일이 있었나
기억 기록 파이프라인을 실제 CLI로 돌렸다. 인물 문서·주인공 문서·연대기·state가 모두 갱신됐고, 원본 설정 부분은 그대로였다. 기능은 통과였다. 그런데 기록된 **내용**을 읽어 보니 우리가 정한 기준(§7.4)을 네 가지나 어기고 있었다.

## 실제 결과에서 찾은 위반
1. **대사 원문 인용** — 인물 관계 항목에 `… "돌려받을 거면 살아서 와요"라는 말로 걱정을 내비침 (t6)`
2. **항목이 사건 로그가 됨** — 관계 한 줄이 3문장 130자. `### 사건`이 같은 내용을 되풀이하고, 정보 전달까지 사건으로 쌓였다(`t4–5: … 추격자 수를 다시 알려줌`)
3. **이미 없는 소지품 잔류** — `얼음 조각을 … 건네 … 더는 지니지 않음 (t3–5)`. 나을 상처(`등에 부러진 화살`)도 "영구적 신체 변화"에 들어갔다
4. **state 오용** — `"location": "능선(한경)·움막(설하, 분리됨)"`. 인물별 위치를 한 칸에 섞어 넣어 상태 패널에 그대로 노출됐다

여기에 연대기가 3턴 범위에 글머리표 7개였다. 프롬프트가 "3~8개"만 요구해서 턴 수와 무관하게 늘어났다.

## 해결
프롬프트(`RecordPrompts.kt`)만 고쳤다. 태그는 그대로여서 파서와 Fake 응답은 건드리지 않았다.
- 공통: 한 줄 한 문장, 대사 인용 금지
- 시나리오 관리자: 글머리표 수 ≤ 턴 수, `location`은 주인공 기준 한 곳, `time`은 며칠째+시각
- 캐릭터 관리자: 관계는 한 문장, 사건은 관계와 중복 금지(대화·정보 전달·이동은 사건이 아니다), 소지품은 지금 가진 것만(넘긴·잃은 줄은 지운다, 나을 상처는 제외)

## 확인 방법
같은 범위를 되돌린 뒤 다시 기록해 비교했다.

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 인물 관계 | 3문장 + 대사 인용 | 1문장, 인용 없음 |
| 인물 사건 | 3줄 | 2줄 (정보 전달 줄 사라짐) |
| 소지품 | 넘긴 얼음 조각 잔류 | 줄 삭제, 지금 가진 것만 |
| 연대기 회차 | 글머리표 7개 | 3개 (턴 3개) |
| `state.location` | `능선(한경)·움막(설하, 분리됨)` | `능선 근처 눈밭` |
| 인물 문서 크기 | 2,868 B | **2,020 B (−30%)** |

측정 조건: 인물 2명 시나리오, 3턴 범위 + 재반영 1턴, CLI 프로바이더(opus), 각 1회.

## 같이 알게 된 수치
- 기억 기록 소요: 22초(3턴, 인물 1, 재반영 없음) vs **110초·128초**(재반영 1턴 포함). 재반영이 붙으면 5배 가까이 걸린다.
- 기록이 도는 동안 채팅은 막히지 않는다.

## 남은 의문 / 다음에 확인할 것
- [ ] 앞선 기록이 남긴 긴 옛 항목은 다시 다듬지 않는다. 압축 단계에 맡기는 게 맞는지 확인이 필요하다
- [ ] 다 **쓴** 소모품은 여전히 남는다("넘긴/잃은" 외에 "소모한"도 명시해야 한다)
- [ ] 문서 예산(3,000자)을 넘길 만큼 길게 진행해 압축 단계가 실제로 도는지 보지 못했다
