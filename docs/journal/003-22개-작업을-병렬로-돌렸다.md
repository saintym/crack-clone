## 무슨 일이 있었나
v2 구현을 작업 21개(T00~T20)로 쪼개고, 동시 4개까지 에이전트를 붙여 돌렸다. 중간에 T21(실제 PostgreSQL 검증)을 추가해 22개가 됐다. 각 작업은 `git worktree`로 폴더를 분리하고, 끝나면 내가 리뷰해서 main에 `--no-ff`로 머지했다. 저장소 커밋은 229개가 됐다.

## 왜 이걸 하고 있었나
작업 사이 의존이 많아서(메시지 저장소 → 채팅 흐름 → 프론트) 순서대로 하면 오래 걸린다. 반대로 아무렇게나 병렬로 돌리면 같은 파일을 동시에 고쳐 충돌 정리에 시간을 다 쓴다.

## 시도한 것들
| # | 시도 | 결과 | 여기서 알게 된 것 |
|---|---|---|---|
| 1 | 작업 명세에 "수정 가능한 파일"을 파일 단위로 적었다 | 효과가 컸다 | T01(AI 호출부)과 T02(경로 계산부)가 같은 `ChatService`·`MemoryService`를 고쳤는데 자동 병합됐다. T09(branch)와 T10(create)도 같은 `StoryService`에서 함수만 나눠 충돌하지 않았다 |
| 2 | 마이그레이션 번호를 미리 배정했다(V4=T02, V5=T03, V6=T12, V7=T14) | 충돌 0건 | 번호를 각자 고르게 두면 반드시 겹친다 |
| 3 | 상태를 각 작업 파일에만 적게 했다 | 충돌 0건 | 보드 한 파일에 상태를 모으면 PR마다 그 줄이 충돌한다 |
| 4 | 에이전트에게 rebase를 맡겼다 | **실패** | 권한 정책이 `git rebase`를 막았다. 에이전트는 우회하지 않고 최신 main을 따로 풀어 자기 변경을 얹어 테스트로 호환성만 확인했다 |
| 5 | 머지를 내가(오케스트레이터) 머지 커밋으로 처리했다 | 채택 | rebase 없이도 통합이 됐다. 충돌 해결 판단을 한 곳에 모을 수 있었다 |

## 실제로 난 충돌

## 예상 못 한 비용
- **확장 지점을 비워 둔 병렬화는 통합 커밋이 따로 필요했다.** T13은 "마지막 기록 턴"을 읽는 인터페이스만 만들고, T14는 그 값을 담는 DB 칼럼만 만들었다. 둘을 잇는 코드와, 테스트 대역 빈이 실제 구현과 겹쳐 터진 `NoUniqueBeanDefinitionException` 정리는 내가 따로 했다.
- **먼저 머지된 작업이 뒤 작업의 명세 전제를 바꿨다.** T16 명세에는 "기여자 빈 2개"라고 적었는데, T13이 이미 같은 일을 하는 기여자를 넣어 둬서 하나만 만드는 게 맞았다. 에이전트가 실제 코드를 기준으로 판단하고 기록했다.
