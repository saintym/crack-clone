## 무슨 일이 있었나
"스토리를 시작하면 그 스토리 전용 Claude Code 에이전트를 띄워 두면 되지 않나. 왜 매 턴 전체 맥락을 다시 보내야 하나"라는 질문이 나왔다. 처음에는 "모델 API가 상태가 없으니 다시 보내야 한다"고만 답했다. 질문이 두 번 더 오고 나서야 **측정해서 답하는 게 맞다**는 걸 알았다. 결과는 예상과 달랐고, 설계 결정이 두 개 바뀌었다.

## 확인한 사실
| 확인 | 결과 |
|---|---|
| 지금 구현이 프로세스를 띄워 두는가 | 아니다. 매 턴 `claude -p … --no-session-persistence`로 새로 띄우고 종료한다 |
| CLI가 세션 유지를 지원하는가 | 한다. `--input-format stream-json`(실시간 입력), `--resume`, `--fork-session` |

## 측정 1 — 프롬프트 크기와 지연
`claude -p`에 프롬프트를 직접 넣고, 출력을 "한 문장"으로 고정해 입력 크기 효과만 봤다. 각 3회, 같은 기계(M 계열 맥), opus 모델.

| 입력 | 첫 토큰까지 | 전체 |
|---|---|---|
| 3,055자 | 3.40 / 3.58 / 5.75초 | 6.05~8.54초 |
| 30,055자 | 3.22 / 3.61 / 4.84초 | 6.32~7.72초 |
| 85,041자 | 4.34 / 4.46 / 4.75초 | 7.01~7.25초 |

입력이 28배 커져도 지연이 거의 같다. 앞선 검증에서도 delta 33개는 18초, 324개는 26초였다. **지연을 좌우하는 건 출력 길이다.**

## 측정 2 — 캐시 (결정적이었다)
같은 60,000자(약 43K 토큰) 프롬프트를 **새 프로세스로 연속 2회** 호출하고 `result` 이벤트의 usage를 읽었다.

| | 1회차 | 2회차 |
|---|---|---|
| 캐시 쓰기 | 30,911 토큰 | 0 |
| 캐시 읽기 | 11,945 토큰 | **42,856 토큰** |
| 비용 | $0.2565 | **$0.0161** |
| 세션 ID | 서로 다름 | 서로 다름 |

CLI는 이미 프롬프트 캐싱을 적용하고 있고, **프로세스가 달라도 접두사가 같으면 캐시를 읽는다.** 16배 저렴했다.

## 결정
- **세션 유지는 하지 않는다(D29).** 얻으려던 이득(캐시)을 이미 얻고 있다. 반대로 세션을 쓰면 오래된 원문 정리가 불가능해지고(v2의 핵심이 무너진다), 메시지 수정·삭제·재생성·분기가 DB와 어긋난다. 세션 상태가 CLI 저장소에 남아 스토리 격리와 백업에서도 빠진다.
- **활성 인물 집합을 기억 기록 회차 동안 고정한다(D30).** 캐시는 접두사 일치다. 지금은 활성 인물이 매 턴 바뀌어 프롬프트 앞부분이 달라진다. 그러면 매 턴 캐시를 새로 써서 위 표의 차이(16배)를 그대로 낸다. 새 인물이 언급되면 추가하고, 제거는 기록 시점에만 한다.

## 여기서 알게 된 것
"프롬프트를 줄여야 한다"는 직관은 맞았지만 **근거가 틀렸다.** 지연 때문이 아니다. 실제 이유는 셋이다. ① 출력 품질(AI가 필요한 정보에 집중) ② 접두사 안정성(캐시) ③ API 프로바이더로 바꿀 때의 토큰 비용. 측정 없이 최적화 대상을 정하면 엉뚱한 곳을 고친다.

## 내가 틀렸던 것
- 처음에 "비용을 줄이려고 기억 기록 주기를 10턴에서 3턴으로 낮췄다"고 설명했다. 틀렸다. 주기를 낮추면 플레이 턴당 기록이 더 자주 돈다. 첫 기록을 빨리 보려던 것이었고, 턴 수 상한을 같이 두지 않으면 비용이 늘어난다. 지적을 받고 호출 예산(채팅 12턴, 기록 3~4회)을 따로 정했다.
- 캐시가 이미 동작한다는 사실을 측정 전까지 몰랐다. 세션 유지의 이득을 과대평가한 채로 설계 문서를 쓸 뻔했다.
