## 무슨 일이 있었나
사용자가 "외부에서도 접근이 가능하게 하고 싶어. 인증은 지금처럼 비밀번호로"라고 요청했다. `cloudflared`는 이미 설치돼 있었으니 한 줄이면 열 수 있었다.

열기 전에 방어 상태를 확인했더니 **네 가지가 걸렸다.** 그중 하나는 인증을 통째로 무력화할 수 있는 것이었다. 터널은 네 가지를 다 막은 뒤에 붙였다.

## 왜 이걸 하고 있었나
그동안 이 앱은 같은 와이파이 안에서만 돌았다. 맥에서 Vite(:5173)와 백엔드(:8082)를 띄우고, 폰은 LAN IP로 붙었다. 인증은 [006](./006-인증이-사실상-없었다.md)에서 한 번 크게 고쳤다 — 그때는 토큰 길이만 검사하고 있어서 아무 문자열이나 통과했고, HMAC 서명과 만료를 넣어 막았다.

그래서 "인증은 이미 고쳤다"고 생각하고 있었다. **집 안에서는 맞는 말이었다.**

## 증상 / 막힌 지점
막힌 게 아니라, 점검에서 나온 것이다.

| # | 항목 | 상태 | 왜 문제인가 |
|---|---|---|---|
| 1 | 전송 구간 | 평문 HTTP | 비밀번호가 그대로 흘러간다 |
| 2 | 로그인 시도 | **횟수 제한 없음** | 무제한 대입이 가능하다 |
| 3 | 토큰 HMAC 서명 키 | `crack-local-secret-x7k9` | **맞히면 비밀번호 없이 토큰을 위조한다** |
| 4 | 프론트 | Vite **개발** 서버 | HMR·소스맵 노출. 개발 서버를 인터넷에 두면 안 된다 |

3번이 제일 위험했다. `AuthTokens`는 이렇게 토큰을 만든다.

```
token = base64url("v1:<만료 epoch>") + "." + base64url(HMAC_SHA256(payload, tokenSecret))
```

서버는 토큰을 저장하지 않고 서명만 검증한다. **그러므로 `tokenSecret`을 아는 사람은 비밀번호를 전혀 모르고도 유효한 토큰을 찍어낼 수 있다.** 006에서 막은 것은 "아무 문자열이나 통과하는 것"이었지, 키가 약한 경우가 아니었다.

저장소에 커밋된 기본값도 확인했다.

```
crack-backend/src/main/kotlin/com/crack/global/auth/AuthConfig.kt:8:
    val tokenSecret: String = "crack-default-secret-change-me",
```

**이 저장소는 public이다.** 설정을 덮지 않고 띄운 사람은 인증이 없는 것과 같다.

그리고 뚫렸을 때 잃는 것이 데이터만이 아니다. 채팅 엔드포인트는 **로컬에서 Claude CLI 프로세스를 띄운다.** 침입자는 남의 맥에서 opus를 돌릴 수 있다.

## 시도한 것들

| # | 시도 | 결과 | 여기서 알게 된 것 |
|---|---|---|---|
| 1 | 프론트를 `vite preview`로 서빙할까 | 버림 | `server.proxy`는 preview에 적용되지 않는다. 프록시 설정을 따로 둬야 하고 공개 포트도 둘이 된다 |
| 2 | 백엔드가 `dist`를 서빙 (`addResourceHandler("/**")` + SPA 폴백 리졸버) | `/chat/17`은 200, **`GET /`가 404** | 루트는 정적 리소스 경로가 **빈 문자열**이라 리졸버 체인까지 오지 않는다 |
| 3 | `addViewControllers`로 `/` → `forward:/index.html` | 200 | 루트만 따로 걸어 주면 된다 |
| 4 | 대입 제한을 IP별로 | 버림 | 터널 뒤에서는 모든 요청의 `remoteAddr`가 `127.0.0.1`이다. `X-Forwarded-For`는 위조할 수 있다 |
| 5 | 대입 제한을 전역으로 | 채택 | 1인용 앱이라 전역 카운터가 단순하고 우회가 불가능하다 |

## 원인
- **진짜 원인:** 인증의 기준이 "같은 와이파이"에서 "인터넷"으로 바뀌었는데, 그 전제에 맞춰 만든 값들(짧은 서명 키, 제한 없는 로그인, 개발 서버 노출)이 그대로였다.
- **확인한 근거:** `AuthTokens.kt`의 서명 검증 코드, `git grep`으로 찾은 커밋된 기본값, `AuthController.login`에 시도 횟수를 세는 코드가 없다는 것.
- **왜 바로 못 찾았나:** 006에서 인증을 고친 기억이 "인증은 끝났다"로 남아 있었다. **고친 것은 검증 로직이지 키의 강도가 아니었다.**

## 해결

### 1. 백엔드가 프론트 빌드를 서빙 (`crack.web.dist-path`)
값이 있으면 그 폴더를 `/**`로 주고, 없는 경로는 `index.html`로 폴백한다. **`/api`로 시작하는 경로는 폴백하지 않는다** — 없는 API는 404·401이어야 한다. 값이 비면(기본) 서빙하지 않으므로 로컬 개발은 Vite 그대로다.

공개 포트가 하나로 줄고, 같은 출처라 CORS도 필요 없어졌다.

### 2. 로그인 대입 제한 (`LoginRateLimiter`)
5회까지 봐주고(오타 여유), 그 뒤로는 실패마다 잠금이 2배로 늘어난다(30초 → 1분 → 2분 …, 상한 15분). 성공하면 초기화. **잠긴 동안에는 비밀번호가 맞아도 429를 준다** — 맞는지 여부 자체를 알려 주지 않기 위해서다.

### 3. 비밀값 교체
`password`와 `token-secret`을 긴 랜덤 값으로 바꿨다. 값은 로컬 `application.yml`에만 두고 문서·명세·로그 어디에도 적지 않았다.

### 4. Cloudflare 빠른 터널
`cloudflared tunnel --url http://localhost:8082`. 계정이 필요 없고 HTTPS가 붙는다.

### 확인 방법
```
$ for i in 1..7; curl -X POST .../api/auth/login -d '{"password":"wrong"}'
시도 1 -> 401   시도 2 -> 401   시도 3 -> 401   시도 4 -> 401
시도 5 -> 401   시도 6 -> 429   시도 7 -> 429

$ curl -X POST .../api/auth/login -d '{"password":"<맞는 비밀번호>"}'
{"status":429,"error":"Too Many Requests"}      ← 잠긴 동안에는 맞아도 429

$ curl -o /dev/null -w '%{http_code}' https://<터널>/            → 200
$ curl -o /dev/null -w '%{http_code}' https://<터널>/chat/17      → 200
$ curl -o /dev/null -w '%{http_code}' https://<터널>/api/scenarios → 401
$ curl -o /dev/null -w 'scheme=%{scheme} http=%{http_version}'     → scheme=HTTPS http=2
```
백엔드 테스트 556개 통과(신규 6개), 프론트 build·lint 통과.

## 왜 이 방법을 골랐나
- **버린 대안 — Tailscale:** 가장 안전하다(인터넷에 공개하지 않는다). 대신 접속할 기기마다 설치·로그인이 필요하고 남에게 링크를 줄 수 없다. 사용자가 공개 접속을 원해서 버렸다.
- **버린 대안 — 명명 터널:** 주소가 고정되고 부팅 자동 시작도 걸 수 있다. Cloudflare 계정과 그곳에 네임서버가 올라간 도메인이 필요하다. 지금은 바로 써보는 쪽을 택했다.
- **버린 대안 — Cloudflare Access(추가 인증 계층):** "인증은 지금처럼 비밀번호로"라는 요구와 어긋난다.
- **이 선택으로 포기한 것:**
  - **주소가 끌 때마다 바뀐다.** 빠른 터널은 랜덤 서브도메인이다.
  - **프론트 자동 반영을 잃었다.** 외부로 나가는 건 `dist`라 고칠 때마다 `npm run build`가 필요하다.
  - **전역 대입 제한은 주인을 잠글 수 있다**(가벼운 DoS). 20자 랜덤 비밀번호에 대입은 애초에 무의미하므로, 뚫리는 것보다 잠깐 기다리는 쪽을 택했다.

## 남은 의문 / 다음에 확인할 것
- [ ] 커밋된 기본 `tokenSecret`을 쓰고 있으면 **기동 시 경고**를 남기는 것 — BUG-021 수정안에 적혀 있었는데 아직 안 들어갔다. public 저장소라 남이 그대로 띄울 수 있다
- [ ] 대입 제한이 메모리라 재시작하면 풀린다. 재시작을 유도할 수 있는 경로가 있는지
- [ ] URL 가져오기(T28)의 SSRF 방어가 외부 공개 상태에서도 충분한지 — 이제 남이 이 기능을 호출할 수 있다
- [ ] 터널을 오래 띄웠을 때 끊김·재연결 동작
