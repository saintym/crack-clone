# 병렬 작업 운영 가이드

> 작업 목록과 의존 관계: [docs/tasks/README.md](./tasks/README.md) · 에이전트 규칙: [CLAUDE.md](../CLAUDE.md)
> 이 문서는 **사람(운영자)** 이 여러 에이전트 세션을 어떤 순서로 띄우고, 어떻게 머지할지 정리한 것이다.

---

## 1. 실행 방식 두 가지

| | A. 로컬 worktree | B. 리모트 세션 (Claude Code on the web) |
|---|---|---|
| 작업 공간 | 작업마다 `git worktree`로 폴더를 분리한다 (`../crack-clone-wt/T07`) | 세션마다 GitHub에서 따로 클론. worktree가 필요 없다 |
| 시작 기준 | 로컬 `main` 또는 `origin/main` 중 최신 | **GitHub의 `main`**. 의존 작업이 머지되면 push까지 해야 다음 작업을 시작할 수 있다 |
| 장점 | 로컬 DB, 실제 CLI, 실제 데이터로 확인할 수 있다 | 내 컴퓨터 자원을 쓰지 않는다. 세션을 띄워 두고 다른 일을 할 수 있다 |
| 적합한 작업 | 실제 AI 응답 품질을 봐야 하는 작업(T13, T14 프롬프트 튜닝), 앱을 띄워 확인하는 프론트 작업 | 순수 로직과 테스트로 끝나는 작업(T01~T03, T05, T06, T08~T10, T12, T16, T17) |

두 방식을 섞어 써도 된다. 어느 쪽이든 규칙은 같다: **작업 1개 = 브랜치 1개 = PR 1개**, 작업 파일의 범위 준수, 논리 단위 커밋.

## 2. 동시 실행 수

- **권장: 동시에 3~4개.** 웨이브 1은 7개를 동시에 돌릴 수 있지만, 다음 세 가지가 병목이 된다.
  - **리뷰와 머지 속도:** 사람이 PR을 보고 머지하는 속도보다 빨리 만들어 봐야 대기열만 쌓인다.
  - **구독 사용량 한도:** 로컬 Claude 세션 여러 개가 같은 구독 한도를 나눠 쓴다.
  - **머지 충돌:** 동시에 열린 PR이 많을수록 rebase 비용이 커진다.
- **슬롯이 비면 준비된 작업 중 핵심 경로(§3)에 있는 것부터 채운다.** 작은 작업(T00, T05, T06, T10, T17 등)은 남는 슬롯을 메우는 용도로 쓴다.

## 3. 핵심 경로

작업 크기(대략): **S** 반나절 이하 · **M** 하루 · **L** 1~2일

```
T03(M) ─┐
T01(M) ─┴─► T07(L) ──────► T14(L) ─┬─► T15(M) ─┐
T05(S) ────────────────────┘       └─► T16(M) ─┴─► T18(M)
T02(S) ─► T08(M) ─► T10(S) ─► T11(L) ─┘ (T15는 T11도 필요)
```

- **가장 긴 경로:** T01/T03 → T07 → T14 → T15/T16 → T18. 이 경로의 작업이 늦어지면 전체가 늦어진다.
- **거의 같은 길이의 둘째 경로:** T02 → T08 → T10 → T11. T15에서 첫째 경로와 합쳐진다.
- 그래서 **T01, T02, T03을 제일 먼저** 시작한다. T02는 작으니 끝나는 대로 T08을 바로 띄운다.

## 5. 로컬 worktree로 실행하기 (방식 A)

### 5.1 만들기
```bash
# 저장소 루트(메인 worktree)에서
scripts/task-worktree.sh create T07     # ../crack-clone-wt/T07 에 task/T07-chat-flow 브랜치 생성
cd ../crack-clone-wt/T07 && claude      # 세션에서: "T07 진행해"
```

스크립트가 하는 일:
- 작업 파일에 적힌 브랜치 이름을 읽는다.
- 최신 `main`(원격이 앞서 있으면 `origin/main`)에서 브랜치를 딴다. 추적 브랜치는 설정하지 않는다. 실수로 main에 push하는 것을 막기 위해서다.
- gitignore된 `application.yml`만 복사한다. **실제 시나리오 데이터(`data/`)는 복사하지 않는다.**

이미 브랜치가 있으면 그 브랜치로 worktree를 다시 연다(이어서 작업).

### 5.2 worktree끼리 부딪히는 것과 대응

| 자원 | 문제 | 대응 |
|---|---|---|
| **테스트** | 없음 | `./gradlew test`는 H2 인메모리 DB라 worktree마다 독립이다. 동시에 돌려도 된다 |
| Gradle | 데몬이 worktree마다 떠서 메모리를 쓴다(각 0.5~1GB) | 동시 4개까지는 무난하다. 부족하면 `./gradlew --stop` 또는 `--no-daemon` |
| node_modules | worktree마다 따로 필요하다 | 프론트 작업 worktree에서만 `npm ci` |
| **앱 실행 시 DB** | 브랜치마다 마이그레이션(V4~V7)이 달라서, 같은 DB를 쓰면 Flyway 이력이 꼬인다 | **worktree마다 별도 DB를 쓴다.** `createdb crack_t07` 후 `SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/crack_t07` |
| **앱 실행 시 포트** | 백엔드 8082, 프론트 5173이 겹친다 | 백엔드는 `SERVER_PORT=18207 ./gradlew bootRun`. 프론트는 `CRACK_WEB_PORT=15207 CRACK_API_TARGET=http://localhost:18207 npm run dev`(T04 이후 지원) |
| **데이터 폴더** | 실제 데이터를 가리키면 개발 중인 코드가 사용자 데이터를 망가뜨릴 수 있다 | worktree에서는 `CRACK_DATA_PATH`를 **샘플 데이터 복사본**으로 둔다(T08의 `src/test/resources/fixtures/sample-scenario`를 임시 폴더에 복사). 실제 데이터는 머지 후 메인 worktree에서만 쓴다 |

포트 번호 규칙 예: 백엔드 `18200 + 작업번호`, 프론트 `15200 + 작업번호`

### 5.3 정리
```bash
scripts/task-worktree.sh remove T07    # worktree 삭제. main에 머지된 브랜치면 브랜치도 삭제
scripts/task-worktree.sh list          # 남은 worktree 확인
scripts/task-worktree.sh status        # 작업별 상태
```
커밋하지 않은 변경이 있으면 git이 삭제를 거부한다(안전장치).

## 6. 리모트 세션으로 실행하기 (방식 B)
1. 의존 작업이 모두 머지되고 **GitHub `main`에 push된 상태**인지 확인한다.
2. 새 리모트 세션에서 이 저장소를 연다. 기본 브랜치는 `main`이다.
3. "T07 진행해"라고 지시한다. 에이전트는 CLAUDE.md 규칙대로 브랜치를 따고, 작업하고, PR을 올린다.
4. 리모트에는 CLI, API 키, PostgreSQL, 실제 데이터가 없다. 그래서 완료 조건은 "테스트와 빌드 통과"와 "Fake 프로바이더 기반 확인"까지다. 실제 AI로 확인할 것이 있으면 작업 로그에 적어 두게 하고, 머지 후 로컬에서 확인한다.

## 7. 커밋과 머지

### 7.1 커밋 (작업 세션 안에서)
- 작업 하나의 브랜치 안에서 **논리 단위로 나눠 커밋**한다. 예: 스키마 → 서비스 → 테스트 → 문서
- 작업 파일의 상태와 작업 로그 갱신은 별도 커밋으로 한다: `docs(tasks): T07 작업 로그 갱신`
- 다른 작업의 범위에 있는 파일을 고쳤다면, 그 변경을 별도 커밋으로 분리해 리뷰하기 쉽게 한다.

### 7.2 머지 (운영자 또는 메인 worktree의 통합 세션)
- **순서:** 의존 순서대로 머지한다. 같은 라운드 안에서는 **작은 PR을 먼저** 머지해서 큰 PR의 rebase 부담을 줄인다.
- **방식:** `--no-ff` 머지 커밋으로 합친다. 히스토리에서 작업 단위(Txx)가 한 덩어리로 보이게 하기 위해서다.
  - GitHub PR: "Create a merge commit"을 쓰고, squash는 쓰지 않는다. 작업 안의 논리 커밋을 보존하기 위해서다.
  - 로컬:
    ```bash
    git switch main && git merge --no-ff task/T07-chat-flow -m "Merge T07: 채팅 흐름 재작성"
    ```
- **머지 직후 확인 (main에서):**
  ```bash
  (cd crack-backend && ./gradlew test) && (cd crack-frontend && npm run build && npm run lint)
  ```
- **상태를 DONE으로 (main에서, 머지한 사람이):**
  ```bash
  sed -i '' 's/^- \*\*상태\*\*: .*/- **상태**: DONE/' docs/tasks/T07-*.md
  git commit -am "docs(tasks): T07 완료 처리" && git push
  ```
  리모트 방식이면 push까지 해야 다음 작업이 시작할 수 있다.
- **열려 있는 다른 PR:** 머지 후 충돌이 생긴 PR은 해당 세션에 "main으로 rebase해"라고 지시한다.

### 7.3 충돌이 예상되는 조합

범위를 나눠 두었지만 아래 조합은 같은 파일을 건드린다. **먼저 머지된 쪽을 기준으로 나중 쪽이 rebase**한다.

| 조합 | 겹치는 곳 | 권장 |
|---|---|---|
| T01 · T02 | `ChatService`, `MemoryService`(T01은 AI 호출부, T02는 경로 계산부) | T02(작음)를 먼저 머지 |
| T09 · T10 | `StoryService`(T09는 branch, T10은 create) | T10을 먼저 머지 |
| T13 · T14 | `GET /messages` DTO와 `recorded_through_turn` 사용 | T14를 먼저 머지하면 T13이 실제 필드를 쓴다(T13 명세에 두 경우 모두 적혀 있음) |
| T10 · T18 · T20 | `ScenarioDetailPage` 탭 추가 | 탭 등록 부분만 충돌한다. 순서대로 머지 |
| T15 · T18 · T19 | `ChatPage` 탭 등록, `ChatHeader` | 탭 등록 줄만 충돌한다. 순서대로 머지 |
| T07 · T08 | `PromptAssembler` | 설계상 분리됨(T07은 호출만, T08은 본문). 충돌하면 T08 쪽 본문을 유지 |

## 8. 운영 체크리스트 (라운드마다)
- [ ] `scripts/task-worktree.sh status`로 상태 확인. REVIEW인 PR부터 리뷰하고 머지한다
- [ ] 머지 후 main 테스트와 빌드 → DONE 처리 → push
- [ ] 새로 준비된 작업(의존 작업이 모두 DONE)을 확인하고, 핵심 경로 우선으로 빈 슬롯에 배정한다
- [ ] 끝난 worktree 정리(`remove`)
- [ ] 계약(DESIGN.md) 변경 PR이 있었다면, 진행 중인 세션들에 "main 최신 DESIGN.md를 다시 읽어"라고 알린다
