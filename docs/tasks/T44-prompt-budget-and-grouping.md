# T44 프롬프트 예산 — 변형 묶기, 상한 조정, 활성 인물 수 제한

- **상태**: DONE
- **웨이브**: 8
- **의존**: T40, T41, T43
- **브랜치**: `task/T44-image-budget-raise`
- **마이그레이션**: 없음
- **결정**: D43

## 배경
무림천하에 일괄 등록으로 이미지 **450개를 추가해 총 475개**(25명 × 19변형)가 됐다. 그러자 프롬프트에서 변형이 잘렸다.

```
활성 인물: 당월, 장수, 천성현
  당월:   변형 19개
  장수:   변형 19개
  천성현: 변형 12개   ← 19개인데 12개만 (19+19+12 = 50에서 잘림)
```

사용자가 물었다. **"이미지 갯수 한도를 확 줄인 이유는 뭐야? 필요한 경우에만 꺼내 쓰는 방식 아니야?"**

그리고 곧 더 나은 지적을 했다. **"모든 인물의 이미지 변형 상황은 99% 확률로 동일해. 그냥 변형 목록만 건네주고, 상황에 따라 URL 형식에 인물 코드를 가져오면 되는 거 아냐?"**

## 먼저 바로잡을 오해
**"필요할 때 꺼내 쓰는" 방식이 아니다.** AI가 `{{img:휘령_유혹}}`을 쓸 수 있으려면 **그런 변형이 있다는 걸 알아야** 하므로, 쓸 수 있는 목록이 매 턴 프롬프트에 들어간다.

실제로 좁히는 장치는 **활성 인물 선택**(§6.2)이다 — 25명 중 그 턴에 관련된 몇 명만 목록에 오른다. 상한이 필요한 이유는 **활성 인물 수에 상한이 없었기** 때문이다.

## 고친 것 세 가지

### 1. 변형 집합이 같은 인물을 한 줄로 묶는다 (사용자 지적)
```
쓸 수 있는 인물: 당월, 장수, 천성현
이 인물들은 모두 같은 변형을 가진다: 기본, 미소·기쁨, 분노·경멸, …
```
- **변형 이름으로 묶는다.** 설명이 인물마다 다르면(`기본(장수의 기본 이미지)`) 그 변형은 설명 없이 이름만 쓴다 — 공유할 수 없는 정보다
- 설명이 변형 이름과 같으면 뺀다(`미소(미소)` → `미소`)
- 묶음이 여럿이면 집합마다 한 줄(`- 가, 나 — 기본, 미소`), 전부 다르면 예전처럼 인물별 한 줄
- **예산을 "실제로 나열되는 변형 수"로 센다.** 묶이면 같은 예산으로 훨씬 많은 인물이 들어간다

**실측: images 섹션 1,441자 → 857자. 총 프롬프트 16,345자 → 15,761자.**

### 2. `prompt-max-entries` 50 → 120
T20에서 50으로 정했을 때는 **인물당 변형이 1개**여서 25명 전체가 25항목이었다. 19개가 되자 3명만으로 잘렸다. (묶기를 넣은 뒤로는 여유가 많다.)

### 3. 활성 인물 수 상한 `crack.prompt.max-active-characters: 6`
**인물 문서가 프롬프트에서 가장 비싸다** — 실측 1명당 약 1,460자.

| 활성 인물 | `characters` 섹션 |
|---|---|
| 3명 | 4,383자 |
| 6명 | ≈ 8,800자 |
| 25명(상한 없음) | ≈ 36,500자 |

동행 인물이 먼저 남고 키워드로 걸린 인물부터 잘린다. 잘리면 INFO 로그에 버린 인물을 남긴다.

## 작업 로그

### 2026-09-29
**사용자의 지적이 설계를 바꿨다.** 나는 "예산을 올리자"로 끝내려 했는데, 사용자가 **"변형 집합이 어차피 같으니 한 번만 주면 된다"**고 했다. 맞는 말이고 훨씬 낫다 — 크기가 줄고 뜻도 분명해진다(AI가 "모든 인물이 같은 변형을 가진다"를 바로 안다).

**두 번 막혔다.**
1. **처음엔 안 묶였다.** `기본`의 설명이 인물마다 달랐다(`기본(장수의 기본 이미지)`). T27의 인물별 편집기로 넣은 옛 항목들이다. 설명까지 포함해 비교하면 집합이 달라진다 → **변형 이름으로 묶고 설명은 묶음 안에서 같을 때만** 붙이도록 고쳤다
2. **테스트가 NPE로 죽었다.** 테스트 인물 이름을 `가`, `나`, `다`로 지었는데 `KeywordMatcher.MIN_KEY_LENGTH`가 2라 **한 글자 이름은 키워드로 잡히지 않는다.** 활성 인물이 0명이 되어 기여자가 null을 돌려줬다. 두 글자로 바꿨다. 이 제약을 DESIGN §6.2에 적어 뒀다 — 실제 시나리오에서도 한 글자 이름을 쓰면 같은 일이 난다

**활성 인물 상한을 이미지 때문에 걸지는 않았다.** 묶기 덕에 이미지 쪽은 여유가 생겼다. 그래도 상한을 둔 이유는 **인물 문서가 훨씬 비싸기** 때문이다(1명당 1,460자 대 이미지 목록 전체 857자).

**다음 작업자에게:**
- 예산(`prompt-max-entries`)은 이제 **나열되는 변형 수**를 센다. 항목 수가 아니다
- 활성 인물 상한은 인물 문서 크기 때문이다. 인물 문서를 줄이면(T24 다이제스트) 상한을 올릴 여지가 생긴다
- 한 글자 인물 이름은 키워드로 잡히지 않는다. 시나리오를 만들 때 주의한다
