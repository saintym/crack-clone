## 구현 내용
DESIGN.md §8.6이 기준이다. 형식과 규칙은 거기 표로 정리했다.

- **API**: `POST /api/scenarios/{name}/images/bulk`, body `{spec, apply}`. `apply=false`면 미리보기만
- **적용은 덧붙이기만 한다.** 기존 줄과 주석은 건드리지 않고, 이미 있는 태그는 건너뛴다
- **화면**: 시나리오 상세 → 이미지 탭 아래 「주소 규칙으로 일괄 등록」. 미리보기를 먼저 보여 준다

## 설계 판단 — 규칙을 보관하지 않고 펼쳐서 넣는다
사용자가 대안을 냈다. "이미지 전용 agent를 두고 링크를 요청하거나, 프론트에서 출력에 해당하는 링크를 백엔드에 요청해서 받는 것도 괜찮고."

**뒤쪽 절반은 이미 그렇게 동작한다.** 프론트는 메시지에 주소를 박지 않는다. `GET /api/stories/{id}/images`로 카탈로그를 받아 렌더 시점에 태그→주소로 바꾼다. 저장 형태가 목록이든 규칙이든 **프론트 흐름은 달라지지 않는다.**

**앞쪽(전용 에이전트)은 버렸다.** 코드→주소 매핑은 결정론적이라 LLM이 필요 없고, 매 턴 추가 호출은 제품 원칙에 어긋난다.

**규칙만 보관하는 방식도 버렸다.** 그럴듯해 보이지만 목적을 달성하지 못한다.
1. **프롬프트에는 결국 "쓸 수 있는 변형 목록"을 줘야 한다.** AI가 무엇을 고를 수 있는지 알아야 하므로 어차피 펼쳐야 한다. **프롬프트 크기 문제가 해결되지 않는다**(그건 T40의 예산 순서 수정으로 해결됐다)
2. **인물마다 있는 행동이 다른 경우를 구별할 수 없다.** 완안연에게 `화남`이 있고 신소향에게 없으면 규칙은 둘 다 있다고 본다 → 404 이미지
3. **한 장만 예외인 주소**(다른 도메인, 다른 확장자)를 다룰 수 없다

펼쳐 두면 **사용자가 그 줄만 지우거나 고칠 수 있다.** 그래서 "규칙으로 생성하고 결과를 파일에 둔다"를 택했다.

## 작업 로그

### 2026-09-28
**변형 이름에서 `/`를 잘라야 했다.** 라벨이 `기본/대화`, `실망/삐짐/정색`처럼 여러 낱말인데, `/`는 `[인물: 이름/변형]`의 변형 구분자라 태그에 들어가면 첫 줄 태그 파싱이 깨진다. **첫 조각을 변형 이름으로, 라벨 원문을 설명으로** 나눴다. 설명이 프롬프트에 들어가므로 정보가 사라지지 않는다 — `- 완안연 — 기본(기본/대화), 실망(실망/삐짐/정색)`.

**범위는 같은 라벨을 여러 장에 준다.** `3~4: 놀람`이면 `놀람`, `놀람2`가 된다. 태그가 중복이면 카탈로그 파서가 첫 항목만 인식하므로 번호를 붙여야 한다.

**행동 구역을 하나로 합쳤다.** 명세에 `# 행동`과 `#H`처럼 구역이 여러 개 오는데, 카탈로그에서는 둘 다 그냥 변형이다. **제목에 `캐릭터`가 있는 구역만 캐릭터 표로 보고 나머지는 전부 행동 표**로 합친다.

**확인:** 584개 통과. 실제 명세(인물 2명 × 행동 5개)로 서버에 요청해 10개가 나오고 `https://pj.knotta.org/F01_3.png` → `완안연_웃음`이 되는 것을 확인했다.

**다음 작업자에게:**
- 적용은 **덧붙이기만** 한다. 표를 고쳐 다시 돌리면 기존 태그는 건너뛰고 새 것만 붙는다. 주소가 바뀐 경우는 반영되지 않는다 — 그 줄을 지우고 다시 돌려야 한다
- 존재하지 않는 조합은 사용자가 정리한다. 카탈로그에 있어도 이미지를 못 불러오면 프론트가 숨기지만, 그 턴은 이미지가 없어진다
